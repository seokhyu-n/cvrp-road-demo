## 2. 왜 아직 OR-Tools보다 11~13% 긴가

1. **학습량 부족:** 3,000 step × 512개 ≈ 150만 문제. 원 논문(Attention Model)은 같은 크기에서 1억 개 이상 학습.
2. **회차 분할이 단순:** 방문 순서대로 싣다가 넘치면 복귀(greedy split). 같은 순서라도 끊는 위치에 따라 거리가 달라짐.
3. **회차 간 개선 없음:** 2-opt는 회차 안에서만. 고객을 다른 회차로 옮기거나 맞바꾸지 않음.

## 3. 개선 계획 (추천 순서)

### 3-1. GitHub Actions CI (30분)
- push·PR마다 `pytest` 실행. CPU torch 설치(`--index-url https://download.pytorch.org/whl/cpu`) + `requirements-dev.txt`.
- 테스트는 OSRM을 가짜로 바꿔서 네트워크 없이 돈다. OR-Tools 테스트는 ortools가 있으면 실행.
- README에 배지 추가.

### 3-2. 후처리 강화 — 학습 없이 (반나절~하루)
- **최적 분할(Split DP, Prins 방식):** 모델의 고객 방문 순서(giant tour)를 고정하고, 용량을 지키며 총 거리가 최소가 되도록 회차 경계를 동적계획법으로 정한다. O(n²), 20~50명이면 매우 빠름. `cvrp/solver.py`의 `split_trips_capacity_only` 옆에 추가하고 옵션으로 비교.
- **회차 간 지역 탐색:** relocate(고객 한 명을 다른 회차로), swap(두 회차의 고객 교환), or-opt(1~3명 구간 이동), 2-opt*. 용량 확인 필수. 도로 거리는 비대칭이므로 delta 계산 주의.
- 평가: 같은 평가셋으로 한 번에 한 가지씩 Run 기록(예: F = E + Split DP, G = F + inter-route LS). 직선·도로 둘 다.
- 데모 응답 시간이 크게 늘지 않는지 확인(후보 33개 각각에 적용하면 느려질 수 있음 → 최종 후보 몇 개에만 적용하는 방안).

### 3-3. POMO 방식 재학습 (Colab GPU, 학습 반나절~하루+)
- 구조는 지금과 같은 Transformer 인코더 + 포인터 디코더라 `cvrp/model.py` 재사용 가능.
- 학습: 모든 고객을 출발점으로 한 N개 rollout을 동시에 굴리고, 그 평균을 baseline으로 쓰는 REINFORCE.
- 추론: 좌표 대칭 변환 8가지 × 출발점 N개 중 최단. 데모에서는 후보 수를 줄여 Render 무료 서버 응답 시간 관리.
- 고객 수 20~50 혼합 학습으로 50명 성능 확보. 정규화(창고 중앙)는 학습 데이터 생성과 반드시 일치시킬 것.
- 논문 기준 합성 CVRP에서 최적해 대비 약 1% 안팎. 우리 평가는 OR-Tools 1초·도로 거리 기준이라 그대로 나오진 않음.
- 결과는 **v3**로: 새 체크포인트를 따로 두고, v2 모델과 같은 평가셋으로 비교, README에 v2→v3 추가, `v3.0` 릴리스.
- 대안(비추천): 기존 방식(greedy rollout) 학습만 늘리기 — 같은 수고에 POMO가 효과가 더 큼.

- GitHub About 설명·토픽(cvrp, pytorch, fastapi, osrm, or-tools) — GitHub 화면에서 직접.

## 4. 포트폴리오·면접 메모

- **강점:** 처음부터 끝까지 혼자 만들고 운영(모델·API·UI·배포, 라이브 데모), 측정 기반 개선(고정 평가셋·Run 기록·OR-Tools 참조해·재현 가능), 구체적인 문제 발견 이야기(분포 불일치, README와 데모 설정 불일치, 직선 vs 도로, 스레드 경합, prompt 버그), v1→v2 비포·애프터.
- **약점·예상 질문:**
  1. "OR-Tools가 더 좋은데 왜 딥러닝?" → **전공 과목이 딥러닝**이라 학습 기반 휴리스틱(Attention Model 계열)이 출발점이었다. 처음부터 OR-Tools를 이기는 게 목표가 아니었고, v2에서 OR-Tools를 기준으로 현재 수준(약 11~13% 차이, 13~17배 빠름)을 정직하게 쟀으며, 남은 차이는 학습량 부족으로 보고 POMO 재학습을 다음 단계로 잡았다.
  2. 모델 자체는 v1 그대로 → 3-3 재학습으로 보완.
  3. AI 도움으로 만든 흔적 → 각 개선을 본인이 설명할 수 있어야 함(창고 중앙 정규화 이유, 비대칭 거리에서 2-opt가 달라지는 이유, 스레드 경합 원인 등). v2 개선 6가지를 "왜 문제였나 / 어떻게 확인했나 / 결과" 한 문단씩 직접 써 보기를 추천.
  4. 합성 데이터·20~50명·시간창 없음 → 범위를 솔직히 말하고 확장 방향 제시.
- **직무별:** 백엔드·풀스택·AI 서비스(FDE) 쪽은 강점이 큼. ML 엔지니어·연구 쪽은 재학습 후 강점.

## 5. 작업할 때 알아 둘 것 (환경·함정)

- venv `.venv`, CPU torch. pip는 항상 `python -m pip`.
- 로컬 서버는 `127.0.0.1`로 접속(Windows에서 `localhost`는 IPv6 시도 때문에 약 2초 지연).
- Claude 앱 내장 브라우저(Electron)는 `prompt()`를 지원하지 않음 → 웹 UI에서 쓰지 말 것.
- Render 무료 서버: main 머지 시 자동 배포(약 5분), 오래 안 쓰면 잠들어 첫 접속 30초~1분.
- 공개 OSRM: 초당 1회 정책. 평가용 대량 호출은 `cvrp/road.py` 캐시를 거칠 것.
- 평가 Run을 기록하기 전에 코드를 커밋해야 `git_commit`이 `-dirty`가 아님(runs.csv 자체 변경은 제외됨).
- PowerShell에서 git·gh에 여러 줄 메시지나 따옴표가 든 본문은 파일로 넘길 것(`git commit -F`, `gh pr create --body-file`).
- PR은 squash 머지, 커밋 메시지는 Conventional Commits 접두어 + 한국어.
